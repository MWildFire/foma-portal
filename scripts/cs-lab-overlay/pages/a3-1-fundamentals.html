1. Что такое база данных и зачем она нужна1. What a database is and why it is needed

EN summary — What is a database. A database is a systematically organised store of data, typically arranged across multiple related tables so it can be searched, updated, secured and shared quickly. You interact with databases every day without realising: e-commerce shops track products, customers and stock; social platforms store profiles, posts and messages; hospitals keep patient histories; banks process billions of accurate transactions; online games persist your inventory and progress. The key idea is that data is structured by purpose, not just dumped into a file, so software and people can reason about it reliably.

База данных (database) — это систематически организованное хранилище данных. Данные хранятся логично, обычно в нескольких связанных таблицах, чтобы их можно было быстро искать, обновлять, защищать и совместно использовать. Ты постоянно взаимодействуешь с базами данных, часто этого не осознавая. A database is a systematically organized store of data. Data is stored in a logical way, usually in several linked tables, so that it can be searched, updated, protected and shared quickly. You constantly use databases, often without realizing it.

💡 Представь библиотеку: книги — это записи (rows), полки с разной информацией о каждой книге (автор, название, год) — это поля (columns), а сама полка с однотипными карточками — это таблица (entity). Каталог, в котором всё это устроено и можно быстро найти любую книгу, — это и есть база данных. 💡 Imagine a library: books are records (rows), the shelves with different information about each book (author, title, year) are fields (columns), and a shelf of cards of the same type is a table (entity). The catalogue in which all of this is organized, and in which any book can be found quickly, is what a database is.

When you save the game, your status is written to the database, so that everything is in place when you come back.

2. Плоский файл vs. база данных: зачем вообще нужны БД2. Flat file vs. database: why databases are needed at all

EN summary — Flat file vs relational. A flat file stores everything in one big table. When the same facts (owner name, vet address) repeat across many rows, you get data redundancy, which causes three classic anomalies. The insert anomaly means you cannot add a new vet until they treat a patient. The delete anomaly means removing one row can wipe out unrelated information. The update anomaly means changing an owner's address in only some rows leaves contradictory copies (data inconsistency). The fix is normalisation: split the flat file into several linked tables, giving you a relational database.

Самый простой способ хранить данные — это плоский файл (flat file): одна большая таблица с одной «сущностью» (entity = table). Звучит удобно, но на практике быстро ломается. Возьмём пример из учебника — ветеринарная клиника, где всё свалено в одну таблицу: владелец, питомец, врач, лечение. The simplest way to store data is a flat file: one large table containing a single entity (entity = table). It sounds convenient, but in practice it breaks down quickly. Let us take an example from the textbook: a veterinary clinic where everything is crammed into one table: owner, pet, vet, treatment.

Нельзя добавить нового врача, пока он не пролечил хотя бы одного питомца. Получается абсурд: вет должен сначала кого-то полечить, чтобы попасть в базу. ➖ Аномалия удаления (Deletion anomaly)➖ Deletion anomaly

Нельзя удалить лечение, не потеряв заодно информацию о враче, питомце или владельце. For example, if you delete all the records about the vet Lucy, you will also lose the data about the cat Seb.

✏️ Аномалия обновления (Update anomaly)✏️ Update anomaly

Если владелец Alison сменит адрес и ты обновишь только одну строку — в базе будут две разных версии её адреса, и непонятно, какая правильная. Это называется data inconsistency (несогласованность данных).If the owner Alison changes her address and you update only one row, the database will contain two different versions of her address, and it is unclear which one is correct. This is called data inconsistency.

Почему вообще не хранить всё в одной таблицеWhy not keep everything in one table?

  • Огромный объём. Повторяющиеся данные занимают много места — и место кончается быстро.Large volume. Repeated data takes up a lot of space, and the space runs out quickly.
  • Сложно масштабировать. Чем больше данных, тем чаще возникают аномалии.Hard to scale. The more data there is, the more often anomalies occur.
  • Неточные расчёты. Любые SQL-запросы и аналитика дадут неправильные результаты, если базовые данные противоречат друг другу.Inaccurate calculations. Any SQL queries and analysis will give wrong results if the underlying data contradict each other.
  • Нет совместного доступа. Один файл — один пользователь за раз; никакой нормальной работы команды.No shared access. One file means one user at a time; there is no proper teamwork.

Решение — разбить плоский файл на несколько связанных таблиц. Это называется нормализация (normalization), а получившаяся структура — реляционная база данных (relational database). The solution is to split the flat file into several linked tables. This is called normalization, and the resulting structure is a relational database.

3. СУБД (DBMS) — что управляет базой3. DBMS: what manages the database

EN summary — DBMS. A Database Management System (DBMS) is the software layer that sits between users (or applications) and the actual data files. It handles efficient storage on disk, executes SQL queries (SELECT, INSERT, UPDATE, DELETE), manages concurrency so multiple users can work without clashing, enforces security and access rights, performs backups and recovery, and maintains data integrity. Common relational DBMSs include MySQL, PostgreSQL, SQLite (embedded, used in browsers and phones), Oracle and Microsoft SQL Server. MongoDB is a popular non-relational (NoSQL) DBMS for document data.

Сама база данных — это просто структурированные файлы на диске. Чтобы их создавать, изменять, искать в них и защищать, нужен специальный софт — система управления базами данных (Database Management System, DBMS). СУБД — это посредник между пользователем (или приложением) и реальными данными. The database itself is just structured files on a disk. To create them, change them, search them and protect them, you need special software: a Database Management System (DBMS). A DBMS is the intermediary between the user (or application) and the actual data.

4. Типы баз данных4. Types of database

EN summary — Database types. The relational model (tables linked by keys, queried with SQL) is the default for structured business data where integrity matters. NoSQL covers document stores (MongoDB), key-value stores (Redis), graph databases (Neo4j) and column stores (Cassandra); these suit flexible schemas, real-time workloads and big data. Object-oriented databases store whole objects (with fields and methods) and fit CAD, multimedia or scientific simulations. Hierarchical databases use a parent-child tree, while network databases let a record have multiple parents — both are largely legacy, though the tree idea survives in file systems and XML/JSON.

5. Ключевые понятия реляционной БД5. Key concepts of a relational database

EN summary — Keys, tables and relationships. A normalised relational database is built from entities (tables/relations), where each row (tuple) is one instance and each column (attribute) is one characteristic. A primary key (PK) uniquely identifies every row and cannot be null. A foreign key (FK) in one table references the PK of another, creating the relationship. A candidate key is any attribute that could serve as the PK; a composite key combines two or more attributes to achieve uniqueness. Relationships have cardinality (1:1, 1:N, M:N) and modality (mandatory or optional), describing how rows in one table relate to rows in another.

Когда плоский файл из ветклиники нормализуют, он превращается в четыре связанных таблицы: OWNER, PATIENT, VET и TREATMENT. Каждая таблица отвечает за одну вещь, а связи между ними строятся через ключи. When the flat file from the vet clinic is normalized, it becomes four linked tables: OWNER, PATIENT, VET and TREATMENT. Each table is responsible for one thing, and the links between them are built with keys.

Любое поле (или комбинация полей), которое могло бы стать первичным ключом — то есть однозначно идентифицирует запись.Any field (or combination of fields) that could become the primary key, that is, one that uniquely identifies a record.
ЗачемWhy it is needed
В таблице может быть несколько уникальных полей: например, в таблице студентов уникальны и Student_ID, и email. Оба — кандидатные ключи. Первичным выбирают только один из них.A table may have several unique fields: for example, in a table of students both Student_ID and email are unique. Both are candidate keys. Only one of them is chosen as the primary key.

🧩 Составной ключ (Composite Key)🧩 Composite key

Что этоWhat it is
Первичный ключ, состоящий из двух или более полей — потому что ни одно поле по отдельности не уникально.A primary key made up of two or more fields, because no single field on its own is unique.
ПримерExample
В таблице TREATMENT поле Patient_ID не уникально (у одного питомца много лечений), но Patient_ID + Date уже уникально — питомец не получает два лечения в один день.In the TREATMENT table, Patient_ID is not unique (one pet has many treatments), but Patient_ID + Date is unique: a pet does not get two treatments on the same day.

🪢 Конкатенированный ключ (Concatenated Key)🪢 Concatenated key

Что этоWhat it is
Ключ, собранный из фрагментов нескольких атрибутов, чтобы получить уникальное значение.A key built from fragments of several attributes to produce a unique value.
ПримерExample
В таблице людей: первые 3 буквы имени + первые 3 буквы фамилии + дата рождения = почти всегда уникально.In a table of people, the first 3 letters of the first name + the first 3 letters of the surname + the date of birth is almost always unique.

Связи между таблицами (Relationships)Relationships between tables

Если у таблиц нет связей, данные «лежат в одиночестве» и пользы от них немного. Связь обозначает, как записи в одной таблице соотносятся с записями в другой. If tables have no links, the data sits in isolation and is of little use. A relationship shows how records in one table correspond to records in another.

Кардинальность (Cardinality) — тип связиCardinality — the type of relationship

1️⃣ Один-к-одному (One-to-One, 1:1)1️⃣ One-to-one (1:1)

Одной записи в одной таблице соответствует ровно одна запись в другой. Пример: один питомец имеет ровно одного владельца (в нашей упрощённой модели).One record in one table corresponds to exactly one record in the other. Example: one pet has exactly one owner (in our simplified model).

1️⃣Ⓜ️ Один-ко-многим (One-to-Many, 1:N)1️⃣Ⓜ️ One-to-many (1:N)

Одной записи в первой таблице соответствует много записей во второй. Пример: один вет выполняет много лечений; один владелец имеет много питомцев.One record in the first table corresponds to many records in the second. Example: one vet carries out many treatments; one owner has many pets.

Ⓜ️Ⓜ️ Многие-ко-многим (Many-to-Many, M:N)Ⓜ️Ⓜ️ Many-to-many (M:N)

Много записей в первой связаны с многими во второй. Пример: много студентов записаны на много курсов. Реализуется через промежуточную таблицу-связку.Many records in the first table are linked to many in the second. Example: many students are enrolled on many courses. It is implemented through an intermediate linking table.

Модальность (Modality) — обязательность связиModality — whether the link must exist

❓ Опциональная связь (Optional)❓ Optional link

Связь может быть, а может и не быть. Пример: «Актёр — ТВ-шоу». Актёр не обязан сниматься в сериале (может играть только в театре).The link may exist or may not. Example: "Actor — TV show". An actor does not have to appear in a TV series (they may act only in the theatre).

❗ Обязательная связь (Mandatory)❗ Mandatory link

Связь должна быть. Пример: «Чек — Товары». Чтобы существовал чек, в нём обязан быть хотя бы один товар.The link must exist. Example: "Receipt — Items". For a receipt to exist, it must contain at least one item.

6. Целостность данных (Data Integrity)6. Data integrity

EN summary — Data integrity. Integrity rules keep stored data accurate, consistent and trustworthy. Entity integrity requires every row to have a unique, non-null primary key, so no record is ambiguous. Referential integrity requires every foreign key to point at an existing primary key (or be null where the link is optional), which prevents orphan records. Domain integrity restricts each column's values to a defined type and range, blocking nonsense like negative ages or text in a numeric price field. On top of these, relational DBMSs enforce ACID properties on transactions — Atomicity, Consistency, Isolation and Durability — so multi-step operations such as a bank transfer either fully succeed or fully roll back.

Целостность данных — это набор правил, гарантирующих, что данные в базе точные, согласованные и достоверные. Без неё база — мусорка с противоречиями. Различают три классических типа. Data integrity is a set of rules that guarantee that the data in the database is accurate, consistent and reliable. Without it, a database is just a rubbish heap of contradictions. There are three classic types.

🆔 Целостность сущности (Entity Integrity)🆔 Entity integrity

ПравилоRule
Каждая строка должна иметь уникальный, непустой первичный ключ. Не может быть двух строк с одинаковым PK; PK не может быть NULL.Every row must have a unique, non-empty primary key. Two rows cannot have the same PK, and the PK cannot be NULL.
ЗачемWhy it is needed
Гарантирует, что мы всегда можем однозначно сослаться на запись. Без этого нельзя сказать «удали строку с Patient_ID = 1011», если таких строк несколько.It guarantees that we can always refer to a record unambiguously. Without it, we cannot say "delete the row with Patient_ID = 1011" if there are several such rows.
Пример нарушенияExample of a violation
Два пациента с Patient_ID = 1011 — запутаемся, какого Оскара лечили.Two patients with Patient_ID = 1011: we would not know which Oskar was treated.

🔗 Ссылочная целостность (Referential Integrity)🔗 Referential integrity

ПравилоRule
Внешний ключ должен указывать на существующий первичный ключ в связанной таблице (или быть NULL, если связь опциональна).A foreign key must point to an existing primary key in the linked table (or be NULL if the link is optional).
ЗачемWhy it is needed
Не должно быть «висящих» ссылок: питомца, чей Owner_ID указывает на несуществующего владельца.There must be no "dangling" references: a pet whose Owner_ID points to an owner who does not exist.
Пример нарушенияExample of a violation
В PATIENT записан Owner_ID = 9999, но в OWNER нет такого ID. Это orphan record — «сирота».PATIENT has Owner_ID = 9999, but there is no such ID in OWNER. This is an orphan record.

📐 Доменная целостность (Domain Integrity)📐 Domain integrity

ПравилоRule
Значения в каждом столбце должны соответствовать заданному типу и допустимому диапазону. Это включает тип данных (INT, VARCHAR, DATE), ограничения (NOT NULL, CHECK), формат.Values in each column must match the specified data type and allowed range. This includes the data type (INT, VARCHAR, DATE), constraints (NOT NULL, CHECK) and the format.
ЗачемWhy it is needed
Защищает от «мусора»: возраст не может быть отрицательным, цена не может быть «hello», дата рождения не в 3025 году.It protects against "junk" data: an age cannot be negative, a price cannot be "hello", a date of birth cannot be in the year 3025.
Пример нарушенияExample of a violation
В поле Cost (число) кто-то записал «бесплатно». В поле Type (Dog/Cat/Hamster) — «бутылка».Someone entered "free" in the Cost field (a number). Someone entered "bottle" in the Type field (Dog/Cat/Hamster).

Бонус: ACID — четыре буквы надёжных транзакцийBonus: ACID — the four letters of reliable transactions

Реляционные СУБД соблюдают ACID-свойства для транзакций (нескольких операций, выполняемых как единое целое): Relational DBMSs follow the ACID properties for transactions (several operations carried out as a single unit):

  • A — Atomicity (атомарность): либо вся транзакция выполняется, либо ни одна её часть. Пример: при банковском переводе либо обе операции (списать у А, зачислить Б) проходят, либо ни одна.A — Atomicity: either the whole transaction is carried out, or none of its parts are. Example: in a bank transfer, either both operations (debit A, credit B) go through, or neither does.
  • C — Consistency (согласованность): транзакция переводит базу из одного валидного состояния в другое.C — Consistency: a transaction moves the database from one valid state to another.
  • I — Isolation (изолированность): одновременные транзакции не мешают друг другу.I — Isolation: concurrent transactions do not interfere with each other.
  • D — Durability (устойчивость): после успешного коммита данные сохраняются даже при сбое сервера.D — Durability: after a successful commit, the data is kept even if the server fails.

7. Кто работает с базой данных — роли7. Who works with the database: roles

EN summary — Database roles. The Database Administrator (DBA) is the technical specialist who runs the production database: installing and configuring the DBMS, managing security and access rights, taking backups and verifying recovery, tuning indexes and queries for performance, and resolving integrity issues. The database designer works earlier in the lifecycle, gathering requirements, drawing ER diagrams, choosing entities, attributes, keys and relationships, and applying normalisation. The end user never writes SQL directly; they interact through forms, search filters and reports — a cashier scanning items, a patient checking a portal, or you scrolling a social feed all count as end users of an underlying database.

8. Плюсы и минусы реляционной БД8. Pros and cons of a relational database

EN summary — Benefits and limitations. Relational databases give you strong data consistency and integrity (PKs, FKs, constraints), powerful querying through SQL, ACID transactions, fine-grained security, controlled concurrent access for many users, and reduced duplication thanks to normalisation. They are well-supported by mature tooling and huge developer communities. Their limitations show up with very large analytical workloads (column stores or NoSQL scale better), with deeply hierarchical data, and with unstructured content like images, audio or free-form JSON. The rigid schema makes structural changes costly (migrations), and the object-relational impedance mismatch complicates mapping objects in OOP code onto flat tables.

9. Реальные примеры баз данных9. Real examples of databases

EN summary — Real-world databases. An e-commerce system typically has tables for Users, Products, Orders, OrderItems and Categories, linked through 1:N and N:1 relationships, and uses all three integrity rules together. A bank relies on ACID transactions so that money moved between accounts is either fully transferred or fully rolled back; a partial transfer is unacceptable, which is why a DBA's work in finance is high-stakes. A hospital system models complex many-to-many links (patients see many doctors, doctors see many patients) through a junction table such as Appointments, and adds strict role-based access control to satisfy laws like HIPAA or GDPR.

🛒 Онлайн-магазин (e-commerce)🛒 Online shop (e-commerce)

Таблицы: Users (покупатели), Products (товары), Orders (заказы), OrderItems (позиции в заказе), Categories (категории).Tables: Users (customers), Products, Orders, OrderItems (items in an order), Categories.

Связи: один пользователь делает много заказов (1:N). Один заказ содержит много позиций (1:N). Каждая позиция ссылается на товар (N:1).Links: one user places many orders (1:N). One order contains many items (1:N). Each item refers to one product (N:1).

Целостность: нельзя оформить заказ от несуществующего пользователя (ссылочная целостность); нельзя поставить цену «hello» (доменная); каждый заказ имеет уникальный Order_ID (целостность сущности).Integrity: you cannot place an order from a user who does not exist (referential integrity); you cannot set a price of "hello" (domain integrity); each order has a unique Order_ID (entity integrity).

🏦 Банк🏦 Bank

Таблицы: Accounts (счета), Customers (клиенты), Transactions (операции), Branches (отделения).Tables: Accounts, Customers, Transactions, Branches.

Здесь критически важны ACID-свойства: при переводе денег нужно атомарно списать с одного счёта и зачислить на другой — никаких «полусделок». Если сервер упал между операциями — транзакция откатывается целиком.Here the ACID properties are critically important: when money is transferred, it must be atomically debited from one account and credited to another, with no "half-done" deals. If the server crashes between the operations, the transaction is rolled back completely.

DBA в банке — это серьёзная работа: ошибка в БД = потерянные деньги клиентов = регулятивные штрафы.A DBA in a bank has a serious job: an error in the database means lost customer money, which means regulatory fines.

🏥 Больница (медицинские записи)🏥 Hospital (medical records)

Таблицы: Patients, Doctors, Appointments, Prescriptions, Diagnoses, Departments.Tables: Patients, Doctors, Appointments, Prescriptions, Diagnoses, Departments.

Сложные связи (M:N): пациент посещает разных врачей, врач принимает множество пациентов — через промежуточную таблицу Appointments.Complex links (M:N): a patient visits several doctors, and a doctor sees many patients, through the intermediate table Appointments.

Безопасность критична: только лечащий врач имеет доступ к карте пациента (роль-based access). Конфиденциальность защищена законом (HIPAA в США, GDPR в ЕС).Security is critical: only the treating doctor has access to a patient's medical record (role-based access). Confidentiality is protected by law (HIPAA in the USA, GDPR in the EU).

Цель: Совместно спроектировать реляционную базу для школьной библиотеки.Goal: Design a relational database for a school library together.

Сценарий: Школьной библиотеке нужна БД для учёта книг, читателей и выдач. Каждая книга может быть выдана много раз; один читатель может одновременно держать несколько книг. Scenario: A school library needs a database to keep track of books, readers and loans. Each book can be loaned many times, and one reader can hold several books at the same time.

Инструкции (группы по 3-4):Instructions (groups of 3-4):

  1. Определи сущности (минимум 3-4): Book, Reader, Loan, возможно Author.Identify the entities (at least 3-4): Book, Reader, Loan, possibly Author.
  2. Перечисли атрибуты каждой сущности и выбери первичные ключи.List the attributes of each entity and choose the primary keys.
  3. Установи связи и определи кардинальность: один читатель → много выдач (1:N); одна книга → много выдач (1:N).Set up the relationships and define the cardinality: one reader → many loans (1:N); one book → many loans (1:N).
  4. Для каждой связи укажи модальность: обязательная или опциональная?For each relationship, state the modality: mandatory or optional?
  5. Подумай, какие правила целостности данных вы будете применять: нельзя выдать несуществующую книгу, дата возврата не может быть раньше даты выдачи и т.д.Think about which data integrity rules you will apply: a non-existent book cannot be loaned, a return date cannot be earlier than the loan date, and so on.
  6. Презентуйте решение классу: ER-диаграмма + 2-3 примера SQL-запросов, которые вы хотели бы поддерживать («показать все книги, которые читатель ещё не вернул»).Present your solution to the class: an ER diagram + 2-3 examples of SQL queries you would like to support ("show all the books that a reader has not yet returned").

Что важно запомнитьKey points to remember

  • База данных = структурированное хранилище с правилами целостности. СУБД (DBMS) — софт, который этим управляет (MySQL, PostgreSQL, SQLite, Oracle).A database = a structured store with integrity rules. A DBMS is the software that manages it (MySQL, PostgreSQL, SQLite, Oracle).
  • Плоский файл приводит к трём аномалиям: insert, delete, update. Поэтому данные разбивают на таблицы — это нормализация.A flat file leads to three anomalies: insert, delete, update. That is why data is split into tables: this is normalization.
  • Каждая таблица — сущность (entity). Строки — записи (tuples). Столбцы — атрибуты (attributes).Each table is an entity. Rows are records (tuples). Columns are attributes.
  • Первичный ключ (PK) — уникальный, непустой идентификатор. Внешний ключ (FK) — ссылка на PK другой таблицы. Так создаются связи.A primary key (PK) is a unique, non-empty identifier. A foreign key (FK) is a reference to the PK of another table. This is how relationships are created.
  • Бывают также: candidate key (любой кандидат на PK), composite key (PK из нескольких полей), concatenated key (склейка из фрагментов).There are also: candidate key (any field that could be the PK), composite key (a PK made of several fields), concatenated key (joined from fragments).
  • Кардинальность: 1:1, 1:N, M:N. Модальность: обязательная или опциональная.Cardinality: 1:1, 1:N, M:N. Modality: mandatory or optional.
  • Три типа целостности: entity (уникальный PK), referential (FK указывает на существующий PK), domain (значения соответствуют типу и диапазону).Three types of integrity: entity (a unique PK), referential (an FK points to an existing PK), domain (values match the type and range).
  • Роли: DBA эксплуатирует БД в проде; проектировщик создаёт схему; конечный пользователь работает через интерфейс.Roles: the DBA operates the database in production; the designer creates the schema; the end user works through an interface.
  • Плюсы реляционных БД: целостность, согласованность, SQL, ACID, безопасность. Минусы: жёсткая схема, плохо с big data и неструктурированными данными — там лучше NoSQL.Advantages of relational databases: integrity, consistency, SQL, ACID, security. Disadvantages: a rigid schema, poor handling of big data and unstructured data, where NoSQL is better.
  • На экзамене популярные вопросы: «опиши X аномалий», «объясни PK и FK», «приведи пример 1:N», «два преимущества реляционной БД». Всегда давай определение + пример.Popular exam questions: "describe X anomalies", "explain PK and FK", "give an example of 1:N", "two advantages of a relational database". Always give a definition + example.
