Трансляция HLTranslation HL

Эта тема (A1.4 — Translation, только HL) — про то, как код, который ты пишешь на Python, Java или C++, превращается в машинные инструкции, которые понимает процессор. Есть три основных подхода: компилятор (compiler) переводит всю программу заранее, интерпретатор (interpreter) — строка за строкой во время выполнения, а JIT (just-in-time) — гибрид, который компилирует «на лету». Каждый подход — это компромисс между скоростью разработки, скоростью выполнения, портируемостью и моментом обнаружения ошибок. This topic (A1.4 — Translation, HL only) is about how code that you write in Python, Java or C++ becomes machine instructions that the processor understands. There are three main approaches: a compiler translates the whole program in advance, an interpreter works line by line during execution, and JIT (just-in-time) is a hybrid that compiles “on the fly”. Each approach is a trade-off between development speed, execution speed, portability and the point at which errors are detected.

1. Что такое трансляция и зачем она нужна1. What translation is and why it is needed

Процессор (CPU) понимает только машинный код (machine code) — последовательности двоичных бит, каждая из которых кодирует одну простую операцию: «загрузи число в регистр», «сложи два числа», «прыгни на адрес». Эти команды очень близки к железу и зависят от архитектуры (x86, ARM, MIPS — у каждой свой набор инструкций). The processor (CPU) understands only machine code — sequences of binary bits, each of which encodes one simple operation: “load a number into a register”, “add two numbers”, “jump to an address”. These instructions are very close to the hardware and depend on the architecture (x86, ARM, MIPS — each has its own instruction set).

Человек писать в машинных кодах не может: они нечитаемы, привязаны к конкретному процессору и громоздки. Поэтому программисты пишут на языках высокого уровня (Python, Java, C++, JavaScript, Rust, Go и т.д.), а специальные программы — трансляторы — переводят этот код в машинные инструкции. Трансляция (translation) — это и есть процесс превращения человеко-понятного кода в команды, которые исполняет CPU. People cannot write in machine code: it is unreadable, tied to a specific processor and cumbersome. So programmers write in high-level languages (Python, Java, C++, JavaScript, Rust, Go, etc.), and special programs — translators — convert this code into machine instructions. Translation is precisely the process of turning human-readable code into the commands that the CPU executes.

🇬🇧 English summary (click to expand)

A CPU only understands machine code — raw binary instructions tied to a specific architecture (x86, ARM, MIPS). Writing software directly in those bits is impractical, so programmers use high-level languages such as Python, Java or C++. A translator bridges this gap by converting human-readable source into instructions the processor can execute. Between the two extremes sits assembly language: human-readable mnemonics like MOV or ADD that map almost one-to-one onto machine instructions. The program performing that final mnemonic-to-binary step is called an assembler.

🇬🇧 English summary (click to expand)

A compiler translates the whole program once, ahead of time, producing a binary executable that the OS runs directly — fastest at runtime but slowest to rebuild and tied to one OS/CPU pair. JIT compilers sit in the middle: code is shipped as portable bytecode, the VM interprets first, then compiles frequently used (hot) sections to native code that it caches for later calls.

3. Компилятор (Compiler)3. Compiler

⚙️ A. Что делает компилятор⚙️ A. What a compiler does

ОпределениеDefinition
Компилятор переводит исходный код в машинный код один раз, до запуска программы. Результат — бинарный исполняемый файл (binary executable), который ОС загружает в память и CPU исполняет напрямую.A compiler translates source code into machine code once, before the program runs. The result is a binary executable file, which the OS loads into memory and the CPU runs directly.
ЭтапыStages
Лексический анализ → синтаксический → семантический → оптимизация → генерация кода. (См. подробно ниже в разделе 6.)Lexical analysis → syntax analysis → semantic analysis → optimization → code generation. (See section 6 below for details.)
Что хорошоStrengths
  • Скорость выполнения — машинный код выполняется напрямую CPU без накладных расходов на трансляцию.Execution speed — machine code runs directly on the CPU with no overhead from translation.
  • Ошибки ловятся заранее: синтаксические, типовые, многие семантические — компилятор не создаст исполняемый файл, пока их не исправишь.Errors are caught early: syntax errors, type errors and many semantic errors — the compiler will not produce an executable file until you fix them.
  • Оптимизация всей программы — компилятор видит весь код и может переставлять инструкции, удалять «мёртвый» код, инлайнить функции.Whole-program optimization — the compiler sees all the code and can reorder instructions, remove “dead” code and inline functions.
  • Защита исходника — пользователю отдаётся только бинарь, исходный код не нужен.Protects the source code — the user gets only the binary file, and the source code is not needed.
Что неудобноDrawbacks
  • Цикл разработки длиннее: каждое изменение требует пересборки (может занимать секунды или минуты).Longer development cycle: every change needs a rebuild (which can take seconds or minutes).
  • Низкая портируемость: бинарь, собранный под Windows x86, не запустится на macOS ARM — нужна отдельная компиляция под каждую платформу.Low portability: a binary built for Windows on x86 will not run on macOS on ARM — a separate compilation is needed for each platform.
  • На этапе компиляции больше расходуется память (компилятор строит AST, таблицы символов и т.д.).The compilation stage uses more memory (the compiler builds an AST, symbol tables, etc.).
Примеры языковExample languages
C, C++, Rust, Go. Компиляторы: GCC, Clang/LLVM, Microsoft Visual C++ (MSVC).C, C++, Rust, Go. Compilers: GCC, Clang/LLVM, Microsoft Visual C++ (MSVC).

Пример исходника на Rust:Example Rust source code:

fn main() {
    println!("Hello, world!");
}

После команды rustc main.rs компилятор создаёт исполняемый файл main (или main.exe на Windows), который при запуске напрямую выводит строку — без участия Rust-инструментов.After the command rustc main.rs, the compiler creates an executable file main (or main.exe on Windows), which prints the line directly when it is run — without any Rust tools being involved.

🇬🇧 English summary (click to expand)

A compiler converts an entire source file into native machine code before the program is launched, producing a binary that the operating system loads directly. Because the CPU runs that output with no translation overhead, compiled programs are typically the fastest option. Most syntax, type and many semantic errors are caught at build time, and the compiler can optimise across the whole program (inlining, dead-code removal, constant folding). The trade-offs: a longer edit-build-run loop, and binaries that only work on the OS and CPU architecture they were built for. Representative languages include C, C++, Rust and Go; common compilers are GCC, Clang/LLVM and MSVC.

4. Интерпретатор (Interpreter)4. Interpreter

📜 B. Что делает интерпретатор📜 B. What an interpreter does

ОпределениеDefinition
Интерпретатор читает исходный код строка за строкой и исполняет каждую инструкцию на лету. Бинарного файла нет — программа существует только как текст исходника плюс работающий интерпретатор.An interpreter reads the source code line by line and executes each instruction on the fly. There is no binary file — the program exists only as the source text plus a running interpreter.
Как работаетHow it works
  • Берёт следующую строку.Takes the next line.
  • Разбирает её (лексика, синтаксис, семантика — на лету).Parses it (lexical analysis, syntax and semantics — on the fly).
  • Превращает в байткод или внутреннее представление.Converts it into bytecode or an internal representation.
  • Выполняет.Executes it.
  • Если встретилась ошибка — останавливается на этой строке, всё что было до — уже исполнено.If it meets an error, it stops at that line; everything before it has already been executed.
Что хорошоStrengths
  • Очень быстрый цикл разработки: правишь файл, сразу запускаешь — без шага компиляции.Very fast development cycle: you edit the file and run it straight away — with no compilation step.
  • Высокая портируемость: один и тот же скрипт работает на Windows, macOS, Linux, лишь бы стоял интерпретатор.High portability: the same script runs on Windows, macOS and Linux, as long as the interpreter is installed.
  • Меньше памяти под трансляцию (нет промежуточного бинаря).Less memory needed for translation (there is no intermediate binary file).
  • Динамическая типизация чаще всего: меньше «бойлерплейта», быстрее писать.Dynamic typing is common: less “boilerplate” code, so programs are quicker to write.
  • Интерактивность: REPL (Python, JS-консоль) позволяет пробовать код прямо в командной строке.Interactivity: a REPL (Python, the JS console) lets you try code directly at the command line.
Что неудобноDrawbacks
  • Медленнее выполняется: каждая строка переводится заново при каждом запуске.Slower execution: each line is translated again on every run.
  • Ошибки всплывают поздно — только когда строка реально исполнится. Опечатка в редко вызываемой функции может пройти в продакшен.Errors appear late — only when the line is actually executed. A typo in a rarely called function can reach production.
  • Нужен интерпретатор у пользователя — программу нельзя просто «отдать как .exe».The user needs an interpreter — the program cannot simply be handed over as an .exe.
Примеры языковExample languages
Python, JavaScript, Ruby, PHP.

Пример на Python:Example in Python:

print("Hello, World!")

Запуск: python hello.py. Интерпретатор сам разберёт, скомпилирует в байткод и тут же выполнит. Никакого .exe на диске не появится.Run it with: python hello.py. The interpreter itself parses the code, compiles it to bytecode and runs it straight away. No .exe file will appear on the disk.

💬 Реальная история (из учебника): когда команда Кэти Боуман получила первое изображение чёрной дыры, обработка огромных объёмов данных с радиотелескопов делалась на Python — потому что интерпретируемый язык позволял быстро менять алгоритм, прогонять заново и видеть результат, не теряя время на пересборку. 💬 Real story (from the textbook): when Katie Bouman’s team received the first image of a black hole, the huge volumes of data from radio telescopes were processed in Python — because an interpreted language made it possible to change the algorithm quickly, run it again and see the result without losing time on rebuilding.
🇬🇧 English summary (click to expand)

An interpreter reads source code line by line at runtime, parsing and executing each statement on the fly with no separate executable produced. This makes the edit-run cycle nearly instant and gives the same script high portability — anywhere the interpreter is installed, the code runs unchanged. Many interpreted languages also offer an interactive REPL for quick experimentation. The downsides are slower execution (translation happens every run) and the fact that errors only surface when a particular line is actually reached, so a typo inside a rarely-called branch can survive into production. Typical languages: Python, JavaScript, Ruby, PHP.

5. JIT-компиляция и байткод-интерпретаторы5. JIT compilation and bytecode interpreters

⚡ C. JIT (Just-in-time compilation)

ОпределениеDefinition
Гибрид компиляции и интерпретации. Исходник сначала компилируется в байткод (платформо-независимое промежуточное представление), а потом виртуальная машина исполняет этот байткод и «на лету» компилирует «горячие» куски (часто исполняемые) в нативный машинный код, который кэшируется и используется в следующих вызовах.A hybrid of compilation and interpretation. The source code is first compiled to bytecode (a platform-independent intermediate representation), and then a virtual machine executes this bytecode and compiles the “hot” parts on the fly (the frequently executed ones) into native machine code, which is cached and used in later calls.
ЛогикаThe logic
  • Загрузка байткода в VM.The bytecode is loaded into the VM.
  • Сначала байткод интерпретируется — это даёт быстрый старт.At first the bytecode is interpreted — this gives a fast start.
  • VM считает, сколько раз вызывается каждый кусок (метод, цикл).The VM counts how many times each part (a method, a loop) is called.
  • Когда счётчик переваливает порог — кусок компилируется в нативный код и кэшируется.When the counter passes a threshold, the part is compiled into native code and cached.
  • Следующие вызовы того же куска идут уже через кэш — почти со скоростью полностью скомпилированного кода.Later calls of the same part go through the cache — almost as fast as fully compiled code.
ПреимуществаAdvantages
  • Гибкость интерпретации + скорость компиляции: горячие куски быстрые, холодные — гибкие.Flexibility of interpretation + speed of compilation: hot parts are fast, cold parts stay flexible.
  • Адаптивная оптимизация: JIT видит реальное поведение программы (какие типы реально приходят) и оптимизирует под них.Adaptive optimization: the JIT sees the program’s real behaviour (which types actually arrive) and optimizes for them.
  • Портируемость на уровне байткода: один и тот же .class или .dll работает на любой ОС, где есть JVM/CLR.Portability at bytecode level: the same .class or .dll file runs on any OS where the JVM or CLR is installed.
НедостаткиDrawbacks
  • «Прогрев» (warm-up): в начале запуск медленнее, пока JIT не успел скомпилировать горячие части.Warm-up: at first the program runs more slowly, until the JIT has compiled the hot parts.
  • JIT-компилятор сам потребляет CPU и память.The JIT compiler itself uses CPU time and memory.
  • Машинный код, который JIT генерирует, всё равно привязан к текущей платформе — портируется именно байткод.The machine code that the JIT generates is still tied to the current platform — it is the bytecode that is portable.
ПримерыExamples
  • Java + JVM (HotSpot, OpenJ9): .java → javac → .class (байткод) → JVM с JIT.Java + JVM (HotSpot, OpenJ9): .java → javac → .class (bytecode) → JVM with JIT.
  • C# / .NET: .cs → csc → CIL/MSIL → CLR с JIT (RyuJIT).C# / .NET: .cs → csc → CIL/MSIL → CLR with JIT (RyuJIT).
  • JavaScript в браузерах: V8 (Chrome), SpiderMonkey (Firefox), JavaScriptCore (Safari) — все используют JIT.JavaScript in browsers: V8 (Chrome), SpiderMonkey (Firefox), JavaScriptCore (Safari) — all of them use JIT.
  • PyPy — альтернативная реализация Python с JIT, в разы быстрее CPython на математике.PyPy — an alternative implementation of Python with a JIT, several times faster than CPython on mathematical computations.

📦 D. Байткод-интерпретаторы (Bytecode interpreters)📦 D. Bytecode interpreters

ОпределениеDefinition
Байткод (bytecode) — это набор инструкций низкого уровня, но платформо-независимый, спроектированный для эффективного исполнения программной виртуальной машиной. Это не машинный код реального CPU, а команды для «виртуального процессора» (например, JVM или Python VM).Bytecode is a set of low-level but platform-independent instructions, designed for efficient execution by a software virtual machine. It is not the machine code of a real CPU, but commands for a “virtual processor” (for example, the JVM or the Python VM).
ПотокProcess
  • Шаг 1. Исходный код компилируется в байткод (один раз, либо при первом запуске).Step 1. The source code is compiled to bytecode (once, or on the first run).
  • Шаг 2. Байткод-интерпретатор (виртуальная машина) читает эти байты и исполняет.Step 2. The bytecode interpreter (the virtual machine) reads these bytes and executes them.
Где это видноWhere you can see this
  • Python (CPython) — при импорте модуля или повторном запуске Python кэширует скомпилированный байткод в файлах .pyc (папка __pycache__). Это не ускоряет выполнение самого кода, но избавляет от повторной компиляции при следующем запуске.Python (CPython) — when a module is imported or the program is run again, Python caches the compiled bytecode in .pyc files (in the __pycache__ folder). This does not speed up the execution of the code itself, but it avoids recompilation on the next run.
  • Java — компилятор javac делает .class-файлы с байткодом, которые потом исполняет JVM.Java — the javac compiler produces .class files with bytecode, which the JVM then executes.
  • Ruby (YARV) — Yet Another Ruby VM, исполняет байткод.Ruby (YARV) — Yet Another Ruby VM, executes bytecode.
  • Erlang (BEAM) — виртуальная машина для байткода Erlang/Elixir.Erlang (BEAM) — a virtual machine for Erlang/Elixir bytecode.
ПлюсыAdvantages
  • Портируемость — байткод одинаков везде, где есть VM.Portability — the bytecode is the same wherever a VM is available.
  • Быстрее «голой» интерпретации исходника — байткод уже разобран, не нужно повторно делать лексику/синтаксис.Faster than plain interpretation of source code — the bytecode is already parsed, so lexical and syntax analysis do not have to be repeated.
  • Меньший размер — байткод компактнее исходного текста.Smaller size — bytecode is more compact than the source text.
МинусыDrawbacks
  • Без JIT — всё равно медленнее, чем нативный машинный код.Without a JIT, it is still slower than native machine code.
  • Часть ошибок ловится только при исполнении конкретной инструкции байткода.Some errors are caught only when a particular bytecode instruction is executed.
🧩 Где граница между байткодом и JIT? Сам по себе байткод-интерпретатор просто исполняет байты по очереди — без перевода в нативный код. JIT — это слой сверху, который замечает горячие участки и компилирует их в нативный код. Java и C# почти всегда идут с JIT; стандартный CPython — это «чистый» байткод-интерпретатор без JIT (а PyPy — с JIT). 🧩 Where is the boundary between bytecode and JIT? A bytecode interpreter on its own simply executes the bytes one after another, without translating them into native code. JIT is a layer on top, which notices the hot parts and compiles them into native code. Java and C# almost always ship with a JIT; standard CPython is a “pure” bytecode interpreter without a JIT (whereas PyPy has a JIT).
🇬🇧 English summary (click to expand)

Bytecode is a low-level but platform-independent intermediate representation designed for a software virtual machine rather than a real CPU. The source is compiled to bytecode once (Python .pyc, Java .class), and a VM then interprets those instructions on any supported OS. Just-in-time (JIT) compilation is an extra layer on top: the VM counts how often each method or loop runs, and once a section becomes hot enough it is translated into native machine code and cached, so later calls run at near-native speed. JIT also enables adaptive optimisation based on real runtime types. Examples: Java/JVM, C#/.NET CLR, JavaScript engines like V8, and PyPy.

Этап 1 — Лексический анализ (Lexical analysis)Stage 1 — Lexical analysis

Компилятор разбивает исходный текст на токены (tokens): ключевые слова, идентификаторы, операторы, литералы, скобки. Это как «нарезать» предложение на отдельные слова и знаки препинания. На этом этапе ловятся ошибки вроде «неизвестный символ». The compiler splits the source text into tokens: keywords, identifiers, operators, literals and brackets. This is like “cutting” a sentence into separate words and punctuation marks. At this stage, errors such as “unknown character” are caught.

Пример. Для строки print("Hello World!") лексер выделит токены: print (идентификатор/ключевое слово), ( (открывающая скобка), "Hello World!" (строковый литерал), ) (закрывающая скобка). Example. For the line print("Hello World!"), the lexer identifies these tokens: print (identifier/keyword), ( (opening bracket), "Hello World!" (string literal), ) (closing bracket).

Этап 2 — Синтаксический анализ / парсинг (Syntax analysis / parsing)Stage 2 — Syntax analysis / parsing

Поток токенов проверяется на соответствие грамматике языка. Парсер (parser) строит из токенов иерархическую структуру — дерево разбора (parse tree) или абстрактное синтаксическое дерево (AST, abstract syntax tree). Тут ловятся ошибки вроде «не хватает закрывающей скобки» или «после if нет условия». The stream of tokens is checked against the grammar of the language. The parser builds a hierarchical structure from the tokens: a parse tree or an abstract syntax tree (AST). Errors such as “a closing bracket is missing” or “there is no condition after if” are caught here.

Например, выражение print("Hello World!") должно соответствовать структуре «функциональный вызов»: имя функции, за ним скобки, в скобках — аргументы. Если эта структура нарушена — синтаксическая ошибка. For example, the expression print("Hello World!") must match the structure of a “function call”: the function name, followed by brackets, with the arguments inside the brackets. If this structure is broken, it is a syntax error.

Этап 3 — Семантический анализ (Semantic analysis)Stage 3 — Semantic analysis

Парсер уже знает структуру кода. Семантика — это его смысл. Здесь компилятор проверяет: The parser already knows the structure of the code. Semantics is its meaning. Here the compiler checks:

  • Существует ли вызываемая функция (print — существует).Whether the function being called exists (print — it does).
  • Совпадают ли типы (нельзя сложить число и список без явного преобразования).Whether the types match (a number and a list cannot be added without an explicit conversion).
  • Объявлены ли все переменные до использования.Whether all variables are declared before they are used.
  • Совместимы ли типы аргументов с сигнатурой функции.Whether the argument types are compatible with the function signature.

Это самый «умный» из ранних этапов. Семантические ошибки звучат как «variable not declared» или «type mismatch: expected int, got string». This is the “smartest” of the early stages. Semantic errors look like “variable not declared” or “type mismatch: expected int, got string”.

Этап 4 — Оптимизация (Optimization)Stage 4 — Optimization

Компилятор улучшает код, не меняя его поведение: переставляет инструкции, удаляет недостижимый код, разворачивает циклы, сворачивает константы (2 + 3 сразу → 5), инлайнит маленькие функции. Цель — чтобы исполнение шло быстрее или потребляло меньше памяти. У интерпретаторов этот этап обычно ограничен или отсутствует. The compiler improves the code without changing its behaviour: it reorders instructions, removes unreachable code, unrolls loops, folds constants (2 + 3 → 5 straight away), and inlines small functions. The aim is for execution to be faster or to use less memory. In interpreters this stage is usually limited or absent.

Этого этапа нет в интерпретаторах в полном объёме — или он минимальный. Полноценная оптимизация — преимущество именно компиляторов (и JIT, который оптимизирует адаптивно). Interpreters do not have this stage in full — or it is minimal. Full optimization is a particular advantage of compilers (and of the JIT, which optimizes adaptively).

Этап 5 — Генерация кода (Code generation)Stage 5 — Code generation

Финальная стадия. Оптимизированное промежуточное представление превращается в: The final stage. The optimized intermediate representation is turned into:

  • Машинный код для конкретной архитектуры — у «полных» компиляторов (C, Rust, Go).Machine code for a specific architecture — produced by “full” compilers (C, Rust, Go).
  • Байткод — у интерпретаторов и гибридных систем (Python .pyc, Java .class).Bytecode — in interpreters and hybrid systems (Python .pyc, Java .class).

После этого код готов к исполнению: либо ОС запускает бинарь напрямую, либо виртуальная машина / интерпретатор начинает исполнять байткод. After this, the code is ready to run: either the OS runs the binary directly, or the virtual machine / interpreter starts executing the bytecode.

🎯 Запомни мнемонику: «Лена Сидит Семантически и Оптимально Готовит код» — Лексика → Синтаксис → Семантика → Оптимизация → Генерация кода. В интерпретаторе те же первые три этапа, затем сразу генерация байткода и исполнение — без полноценной оптимизации. 🎯 Remember the mnemonic: “Lazy Sheep Sleep On Grass” — Lexical → Syntax → Semantics → Optimization → code generation. In an interpreter the first three stages are the same, then bytecode is generated and executed straight away — without full optimization.
🇬🇧 English summary (click to expand)

Translation moves through five well-defined stages. Lexical analysis splits the source text into tokens such as keywords, identifiers, operators and literals. Syntax analysis (parsing) checks those tokens against the language grammar and builds an abstract syntax tree (AST), catching structural errors like missing brackets. Semantic analysis inspects the meaning of the code — verifying types, checking that variables are declared and functions exist. Optimisation rewrites the intermediate form to run faster or use less memory without changing behaviour (constant folding, dead-code removal, loop transformations). Finally, code generation emits the target output: native machine code for a compiler, or bytecode for a VM-based language.

7. Линкеры и загрузчики (Linkers & Loaders)7. Linkers and loaders

После того, как компилятор превратил каждый .c или .cpp файл в объектный код (.o, .obj) — это ещё не готовая программа. Современные программы состоят из множества файлов и используют стандартные библиотеки (standard library) и сторонние библиотеки. After the compiler has turned each .c or .cpp file into object code (.o, .obj), this is still not a finished program. Modern programs consist of many files and use standard libraries and third-party libraries.

🔗 Линкер (Linker)🔗 Linker

Что делаетWhat it does
Берёт все объектные файлы и нужные библиотеки, склеивает их в один исполняемый файл. Разрешает ссылки между файлами: если в одном файле вызывается printf, линкер находит её в стандартной библиотеке C и подставляет правильный адрес.The linker takes all the object files and the libraries it needs and combines them into a single executable file. It resolves references between files: if one file calls printf, the linker finds it in the C standard library and fills in the correct address.
Виды линковкиTypes of linking
  • Статическая: библиотека «вшивается» внутрь .exe → файл больше, но не нужны внешние зависимости.Static: the library is built into the .exe → the file is larger, but no external dependencies are needed.
  • Динамическая: .exe ссылается на .dll (Windows) или .so (Linux) → файл меньше, но при отсутствии библиотеки программа не запустится.Dynamic: the .exe refers to a .dll (Windows) or .so (Linux) → the file is smaller, but if the library is missing, the program will not run.

📥 Загрузчик (Loader)📥 Loader

Что делаетWhat it does
Часть ОС: когда пользователь запускает программу, загрузчик читает исполняемый файл с диска, размещает его в памяти, настраивает регистры, передаёт управление на первую инструкцию (entry point).Part of the OS: when the user runs a program, the loader reads the executable file from disk and places it in memory, sets up the registers and passes control to the first instruction (the entry point).
ЭтапыStages
  • Читает заголовок .exe / ELF.Reads the .exe / ELF header.
  • Выделяет адресное пространство процесса.Allocates the address space of the process.
  • Копирует код и данные в нужные области памяти.Copies the code and data into the correct areas of memory.
  • При динамической линковке загружает .dll / .so в память.With dynamic linking, loads the .dll / .so files into memory.
  • Передаёт управление CPU на стартовый адрес.Passes control to the CPU at the starting address.
🇬🇧 English summary (click to expand)

Compilation usually produces several object files (one per source file) plus references to library code, none of which can run on their own. A linker stitches these object files together and resolves cross-file references so that a call to a function in another module ends up pointing at the right address. Linking can be static (library code is baked into the executable, making it larger but self-contained) or dynamic (the executable keeps a reference to a .dll or .so that is supplied at runtime). The loader is the part of the OS that reads the finished executable from disk, allocates memory for the process, copies code and data into place, resolves any dynamic libraries and finally jumps to the program's entry point.

8. Когда какой подход выбирать8. When to choose which approach

Программа существует ради задачи. Выбор подхода зависит от того, что важнее: скорость выполнения, скорость разработки, портируемость или баланс. A program exists to solve a task. The choice of approach depends on what matters more: execution speed, development speed, portability or a balance of these.

ИнтерпретаторInterpreter

Быстрая разработка и тестированиеFast development and testing

Стартап-команда прототипирует IoT-приложение для управления умными устройствами в реальном времени. Python или JavaScript позволяют быстро менять код и сразу видеть результат, без шага компиляции. На раннем этапе важна гибкость, а не скорость выполнения.A start-up team is prototyping an IoT application for controlling smart devices in real time. Python or JavaScript let you change the code quickly and see the result straight away, with no compilation step. At an early stage, flexibility matters more than execution speed.

КомпиляторCompiler

Производительность критичнаPerformance is critical

Платформа высокочастотного трейдинга (HFT), где сделки исполняются за микросекунды. C++, Rust или Go компилируются в нативный машинный код, который CPU исполняет напрямую. Игры и VR-приложения — та же логика: каждый кадр должен укладываться в 16 миллисекунд.A high-frequency trading (HFT) platform, where trades are executed in microseconds. Производительность достаточно высокая благодаря JIT-компиляции в JVM. То же относится к C# и .NET.A company is writing a CRM system that must run on Windows, macOS and Linux. Java is compiled to bytecode, which the JVM executes on any OS. Performance is high enough thanks to JIT compilation in the JVM. The same applies to C# and .NET.

ИнтерпретаторInterpreter

Скрипты и автоматизацияScripts and automation

Системному администратору нужно автоматизировать ежедневные задачи: парсинг логов, копирование файлов, отправка отчётов. 🇬🇧 English summary (click to expand)

The right translation approach depends on which property matters most. Pick a compiler (C, C++, Rust, Go) when raw performance, predictable timing or low-level hardware access are critical: operating systems, drivers, game engines, high-frequency trading. Pick an interpreter (Python, JavaScript, Bash) when iteration speed and easy cross-platform distribution outweigh runtime performance: prototypes, automation scripts, data analysis and teaching. Pick a JIT + bytecode stack (Java, C#, modern JavaScript engines) when you want a single artifact that runs on any OS while still getting near-native speed for long-running workloads such as enterprise back-ends, mobile apps and browser-side applications like Google Docs or Figma.

9. Связанные понятия9. Related concepts

Стандартная библиотека (Standard library)Standard library

Готовый набор модулей, классов и функций, который поставляется вместе с языком. У Python это os, json, math и сотни других. У Java это java.util, java.io. Стандартная библиотека сильно облегчает разработку: не нужно реализовывать всё с нуля. A ready-made set of modules, classes and functions that comes with the language. In Python these are os, json, math and hundreds of others. In Java they are java.util and java.io. A standard library greatly simplifies development: you do not need to implement everything from scratch.

Парсер (Parser)Parser

Программный компонент, который анализирует поток входных токенов по правилам грамматики и строит из них иерархическое представление — дерево разбора или AST. Парсеры используются не только в компиляторах: HTML-парсер в браузере, JSON-парсер в API, SQL-парсер в БД — все они работают по той же логике. A software component that analyzes a stream of input tokens according to the rules of a grammar and builds a hierarchical representation from them — a parse tree or an AST. Parsers are used not only in compilers: an HTML parser in a browser, a JSON parser in an API, an SQL parser in a database — they all work on the same principle.

Семантика (Semantics)Semantics

Точный смысл, связанный с конкретной программной конструкцией: «что делает эта инструкция?». В отличие от синтаксиса (как должно быть написано), семантика отвечает за что произойдёт при исполнении. Например, синтаксически правильный код x = y + z семантически ошибочен, если y — это строка, а z — число (в строгом языке). The exact meaning of a particular programming construct: “what does this instruction do?”. Unlike syntax (how something must be written), semantics determines what will happen when it is executed. For example, the syntactically correct code x = y + z is semantically wrong if y is a string and z is a number (in a strictly typed language).

Бинарный исполняемый файл (Binary executable)Binary executable

Файл, который содержит готовые машинные инструкции в формате, понятном конкретной ОС (PE для Windows, ELF для Linux, Mach-O для macOS). ОС умеет загружать такой файл в память и сразу передавать управление CPU. A file that contains ready-made machine instructions in a format understood by a particular OS (PE for Windows, ELF for Linux, Mach-O for macOS). The OS can load such a file into memory and pass control to the CPU immediately.

🇬🇧 English summary (click to expand)

A few supporting terms reappear across this topic. A standard library is the bundle of ready-made modules and functions shipped with a language (Python's os, Java's java.util) so common tasks do not have to be rewritten. A parser takes a stream of tokens and applies grammar rules to build a hierarchical structure, usually an AST; the same idea drives HTML, JSON and SQL parsers, not just compilers. Semantics describes what a construct actually means at runtime, in contrast to syntax which only describes how it must look. A binary executable stores ready-to-run machine instructions in an OS-specific container (PE on Windows, ELF on Linux, Mach-O on macOS).

Языки: Python, JavaScript, Ruby, PHP.An interpreter translates line by line during execution → slow execution, late errors, high portability. Languages: Python, JavaScript, Ruby, PHP.
  • JIT = байткод + компиляция «на лету» горячих участков → гибрид. Языки: Java, C#, JavaScript (V8), PyPy.JIT = bytecode + on-the-fly compilation of hot parts → a hybrid. Languages: Java, C#, JavaScript (V8), PyPy.
  • Байткод — платформо-независимое промежуточное представление, исполняется виртуальной машиной (JVM, CLR, Python VM, BEAM).Bytecode — a platform-independent intermediate representation, executed by a virtual machine (JVM, CLR, Python VM, BEAM).
  • Пять этапов компиляции: Лексика → Синтаксис → Семантика → Оптимизация → Генерация кода.Five stages of compilation: Lexical → Syntax → Semantics → Optimization → Code generation.
  • Парсер строит AST из токенов и проверяет соответствие грамматике; семантика отвечает за смысл (типы, существование функций).The parser builds an AST from the tokens and checks that they match the grammar; semantics is responsible for meaning (types, whether functions exist).
  • Линкер склеивает объектные файлы и библиотеки в один .exe; загрузчик (часть ОС) запускает .exe в памяти.The linker combines object files and libraries into a single .exe; the loader (part of the OS) runs the .exe in memory.
  • На экзамене вопрос «evaluate» — это всегда сильные и слабые стороны. «Distinguish» — контраст по чётким критериям (время, ошибки, портируемость, применимость).In an exam, a question with the command term “evaluate” always means strengths and weaknesses. “Distinguish” means contrast by clear criteria (time, errors, portability, applicability).
  • Машинный код — это бинарные команды, привязанные к архитектуре CPU (x86, ARM, MIPS). Ассемблер — почти один-к-один с машинным кодом, но с читаемыми мнемониками (MOV, ADD, JMP).Machine code is binary commands tied to the CPU architecture (x86, ARM, MIPS). Assembly language is almost one-to-one with machine code, but uses readable mnemonics (MOV, ADD, JMP).
🇬🇧 English summary (click to expand)

Key takeaways for A1.4: translation converts human-readable code into instructions a CPU can execute, and the three core approaches are compilation, interpretation and JIT. Compilers (C, C++, Rust, Go) build native binaries that run fastest but are platform-specific; interpreters (Python, JavaScript, Ruby) translate at runtime and are portable but slower; JIT systems (Java, C#, modern JS engines) start from portable bytecode and selectively compile hot paths to native code. Memorise the five translation stages — lexical, syntax, semantic, optimisation, code generation — plus the roles of the parser (builds the AST), linker (combines object files and libraries) and loader (the OS component that brings the executable into memory).
